## 协作约定

- 小任务可由主 agent 兼任多个角色。项目采用分工时，主 agent 说明预期结果、各自负责的范围和要交回的内容，并负责整合与交付。执行者交回改动和自测结果，测试者记录实际观察到的行为，审查者指出证据支持哪些结论、还有哪些验收条件待验证。影响项目方向的取舍由用户决定，实际体验由用户验收。

- 需求明确的局部修正和布局调整，直接实现并自测。技术选型、关键算法、整体需求或架构边界的变化，先和用户讨论。说明可行方案的利弊、推荐理由、其他方案的代价和未验证之处。必要时提议最小实验，经同意后再做。
- 局部需求有冲突时，先完成不受影响的部分，单列冲突的依据、影响和建议，请用户取舍。若冲突会改变整体目标、验收标准或导致大面积返工，先暂停。已确认的决定不重复询问。
- 写共享文档时使用仓库相对路径或占位符，只记录项目要求的工具和服务。个人目录、设备标识、凭据和原始日志留在本地。
- 按可独立验证、可回滚的逻辑行为提交。同一流程的修复、测试和必要文档可同批。用 `git add -- <文件>` 选择本批内容；同一文件混有不同目的的改动时，按差异块暂存。
- 提交前逐项查看 `git diff --cached`，自问：“撤销这次提交，会不会连另一批的成果也撤掉？”如果会，把无关改动留在工作区，不丢弃、不捎带提交。提交信息用英文 Conventional Commits，如 `fix(captions): keep the last subtitle visible`。
- 批次满足下方完成定义后，由主 agent 在本地提交并报告结果。远程推送由用户本人执行。

## 完成定义

- 修缺陷时先用最小输入重现，记下预期和实际表现。暂时复现不了，就收集缺失的条件。修复后用相同输入重测并覆盖相关回归，审阅本批差异，报告前后结果、证据和未测项。
- 阶段验收前，或关键算法、跨模块改动准备提交时，判断是否需要独立只读审查。用户或项目已有适用授权且工具可用，直接安排；无授权先询问，明确禁止则不安排。审查者只接收原始需求、验收条件、变更和运行入口，不改项目、不提交。主 agent 复核证据和分歧；自行审查时如实注明。
- 能独立验证但尚无可体验流程的改动，对应测试通过后可提交，报告具体测到哪一步。
- 有可体验的效果时，agent 先自测，再带用户走一条最短但完整的流程，说清怎么操作、预期看到什么、请反馈什么现象。有偏差就排查、修复并请用户按原流程复验。只把用户实际试过且符合预期的场景记为通过；本期其余验收条件另行核对。
- 功能已实现但用户尚未实测时，README 和阶段记录写「已实现，待实际验证」。用户选择暂不试用时，只问一次是否仍要提交，经同意可本地提交。
- 代码变更影响文档描述的行为、命令或约定时，同步对应文档。纯内部改动运行相应代码测试即可。
